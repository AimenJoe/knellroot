# 0259 — 최적화 2차: 0258의 다음 후보 셋을 재 보고 고른 것

- 날짜: 2026-11-19
- 상태: 채택(개발판 — 그림은 그대로, 기기 판정은 0258의 체크리스트 100에 함께)
- 사장: "응 다음 후보 진행해" (0258 끝의 후보 셋: 적 빛 셈 GPU로 · 먼 적 간단히 · 상주 칸 크기)

## 먼저 잰 것
재는 도구(0258 `prof`)에 적 그리기 안의 구간을 더 꽂았다(`e.pose`·`m.bake(light)`·`m.cast`·`m.hull`·`b.send`).
부하 80(80마리가 다 보이는 장면, 640×360 가상 화면):

| 적 그리기 안(프레임당 ms) | 전 | 뒤 |
|---|---|---|
| 자세 `e.pose` | 0.09 | 0.09 |
| **정점 빛 셈 `m.bake`** | **5.30**(한 번 최대 2.95) | 4.85(최대 1.01) |
| 외곽선 껍데기 `m.hull` | 1.42(최대 2.60) | 1.20(최대 0.39) |
| 보내기 `b.send` | 0.40 | 0.40 |
| 적 합 | 6.80 | 6.13 |

- 적 그리기의 ¾이 정점마다의 빛 셈이었다. 처음엔 정점마다 스레드 지역 값(룩·하늘빛·달빛·문·굽기 그늘)을 여섯 번 넘게 꺼내는 것을 의심했는데,
  모델마다 한 번 꺼내 두게(`light::LitCtx`) 바꿔도 5.30 → 5.09ms뿐이었다 — **비용은 정점 수 자체**(마리마다 수천 정점 × 변환·빛·복사)다.
- 한 번씩 튀던 최댓값은 **배치가 묶음마다 정점 배열을 0에서 다시 키운 것**(`send`가 `mem::take`로 넘겨 용량을 버렸다 — 1만 정점까지 열네 번 남짓
  다시 잡고 옮긴다)이었다. `draw_mesh`는 빌려 읽기만 하므로 넘긴 배열을 용량째 돌려받게 했다(몸·외곽선 둘 다).

## 정한 것
1. **`LitCtx`**(빛 셈의 프레임 값을 모델마다 한 번): 셈의 차례는 그대로라 그림이 같다(시험 `lit_ctx_rim_matches_the_per_vertex_reads`). 얻은 것은 작지만(≈4%) 되돌릴 까닭도 없다.
2. **배치 배열을 용량째 돌려받기**: 튀는 프레임(최대값)이 줄었다 — 폰에서 끊김으로 보이는 것은 평균보다 이쪽이다.
3. **상주 칸 크기는 12m 그대로**(0258 값): 6·12·24m를 정원·마을에서 견줬더니 차가 재는 흔들림 안(정원 지형 10.07 / 10.22 / 10.67ms) — 칸을 아예 나누지 않으면(1000m)
   정원 지형 12.5·법선 11.1ms로 나빠졌다. 나누는 것은 맞고 크기는 상관없다.
4. **적 빛 셈을 GPU로 옮기지 않는다(지금은)**: 0258 시야 거르기 뒤로 실제 판(정원)의 적 그리기는 **0.5ms**다(한 화면에 보이는 적은 열 안팎).
   셰이더로 옮겨도 변환·복사는 남아 얻는 몫이 많아야 절반이고, 빛(달그늘·툰 단·화로·빛줄기·가장자리)을 셰이더로 다시 짜는 위험이 크다. 실제 판에서 적이 다시 무거워지면(떼 마당 0223 V6 등) 그때 재 본다.
5. **먼 적의 외곽선 생략도 하지 않는다(지금은)**: 같은 까닭(실제 판 열 마리 ≈ 0.2ms) + 외곽선은 그림의 문법(0061)이라 판정 없이 지우지 않는다.

## 남은 것
- 실제 판에서 큰 몫은 지형·법선 패스(둘 다 GPU 일)다 — 가상 화면(소프트웨어 GL)으로는 GPU 몫을 더 나눠 잴 수 없다(Mesa의 아무것도 안 그리는 드라이버 `GALLIUM_NOOP`은 버퍼 올리기에서 죽었다).
  기기의 성능 줄(fps·frame)과 연구소 `render.cull`·`render.ssaa`·`render.rows` A/B가 다음 걸음의 근거다(체크리스트 100).
