# 0016. 선을 모아 그린다 — 잡몹 80을 오래 두면 죽던 것

- 날짜: 2026-11-03
- 상태: 채택·구현(사장: "80개의 적들이 제대로 나오긴 하는데, 오래 두고 기다리면 크래시 나는데?" — Android 핸드헬드 Chrome).

## 무엇을 확인했나(재현 순서)
1. **로직은 아니다**: 그래픽 없이 시나리오 6·7을 20분(72,000틱) 돌림 — 디버그 빌드(정수 넘침 검사)·가만히 기다리기·공격·돌리기 섞기 모두 패닉·NaN 없음.
2. **메모리**: 헤드리스 Chromium에서 7번을 3분 — wasm 메모리 6.2 → 8.6MB에서 멈춤, JS 힙 2~4MB를 오감. 큰 누수 아님.
3. **원인(macroquad 0.4.16 소스로 확인)**: 한 프레임의 그리기 호출이 늘면 `QuadGl`이 호출 칸(`DrawCall`)을 늘리고, 칸마다 GPU 스트림 버퍼를 **정점 10,000 × 40B ≈ 400KB + 색인 5,000 × 2B**로 만들며(`quad_gl.rs` `draw()`), 늘어난 칸은 줄이지 않는다. 우리 렌더는 배우마다 면(삼각형) → 윤곽선(선) → 코(면)라 그리기 모드가 바뀔 때마다 호출이 끊겨 **잡몹 80이면 ~180회 ≈ GPU 72MB**, 오래 두면 다 모여 동시에 예고 부채꼴(+옆선)을 띄우며 더 는다. 메모리가 작은 핸드헬드에서 탭이 죽기에 충분하다(실기 로그는 없음 — 원인 추정의 마지막 고리는 실기 확인이 남았다).

## 결정
- 선(배우·기둥 윤곽선 `box_wires`, 예고 부채꼴의 옆선)은 바로 긋지 않고 모았다가(`render::line`) 한 번에(`flush_lines`) — 옅은 기둥보다 먼저(그 뒤의 선이 가려지지 않게). 면은 면끼리 이어져 한 호출로 묶인다.
- HUD 측정 줄에 `draws N (max M)` — 장면을 띄운 뒤 가장 많았던 호출 수(= 줄지 않는 GPU 버퍼 칸 수).

## 잰 것(헤드리스, 같은 장면)
| 장면 | 전 | 후 |
|---|---|---|
| 잡몹 40 · 상자 | 97~99회 | **12회** |
| 잡몹 80 · 상자 | 179~181회, cpu 3.4~3.8ms | **14회(2분 최대 15)**, cpu 2.0~2.2ms |
| 잡몹 80 · 모델 | 25~27회 | 18회 |
| 7번 2분 wasm 메모리 | 6.2 → 8.6MB | 6.2 → 7.1MB(10초 뒤 그대로) |

## 함께 고친 것
- 0014에서 조준 값 둘을 랩 맨 끝에 더해 `render.model`이 끝이 아니게 됐다 — 사람에게 "랩을 열고 ↑ 한 번 = `render.model`"로 안내했는데 틀려졌고, 성능 스크립트도 엉뚱한 값을 바꿨다. `render.model`을 다시 맨 끝으로(값은 그대로, `docs/tuning-frozen.txt` 순서만), 시험 `render_model_stays_the_last_lab_entry`.
